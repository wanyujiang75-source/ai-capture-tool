# Jenkins 安装包刷新慢

记录日期：2026-10-22。状态：已定位，尚未实施修复。

## 现象与实测

- 桌面构建 weak-network-presets-20261020，Jenkins 查询代码与当前工作树校验值一致。
- 本机安装包列表 API 返回 HTTP 200，耗时 9.210 秒，响应 12,830 字节；设备查询另需约 0.522 秒。
- 按现有逻辑逐请求计时：任务索引 0.073 秒、38 个任务；过滤后共 36 次串行请求，总计 10.064 秒，返回 31 个安装包，无查询错误。
- ai-music-apitest 单任务耗时 6.796 秒。独立复核同一查询耗时 6.723 秒，返回 5,698,466 字节，最近 10 个构建中含 43,020 条报告产物，无 apk/apks/zip 安装包。
- 这些是当次样本，不是持续性能保证；不将本次正常 HTTP 200 推断为此前连接错误的确定原因。

## 根因

- `capture_console/jenkins_source.py` 默认排除 api-test，但未覆盖 apitest，误读接口测试报告任务的完整产物列表。
- 每次刷新串行获取每个任务最近 10 次构建及产物，未利用缓存或构建变化信息；单个慢任务阻塞整份列表。
- `AppState.refreshWorkspaceData` 先等待设备刷新，再查 Jenkins；安装包刷新没有合并重复请求。
- `DeviceAppView.jenkinsContent` 在 loading 时隐藏已有列表，仅显示等待动画，放大用户感知延迟。

## 后续修复建议与验收

1. 精确排除非安装包任务，覆盖 api-test/apitest 命名；测试不得误排正常应用任务。
2. 优先查询轻量构建信息，复用未变化构建的产物结果；手动刷新仍检查新构建，失败不伪装成最新数据。
3. 用有界小规模并发查询并合并重复刷新，限制服务器负载；慢任务、权限失败要有明确部分失败状态。
4. 刷新保留已有列表并显示更新状态；验证成功替换、失败保留、重复点击和切页行为。
5. 保持“最近构建中成功且有可安装产物”的选择语义，覆盖最新成功构建无 APK、旧构建有 APK 等回归。
6. 同网络条件记录优化前后总耗时、请求数、响应字节和列表一致性；不得靠删去有效安装包提高速度。

本轮只记录，不修改服务器配置、不触发构建、不下载或安装 APK、不发布远端。
