# Android 真机免 Root 抓包实施计划书

日期：2026-11-10。版本：评审稿 V1。

## 一、目标与结论

目标：让桌面端识别 Android 真机和当前应用，检查抓包条件；对满足条件的原版应用记录并展示完整业务 Request/Response，同时保留用户现有 VPN。

重点验证 PokeHub、StickerHub、MelodyCraft、Wishly。每个应用独立验收，不以其他应用或浏览器通过替代。

当前结论：尚无已验证的方法能在现有一加上，同时满足“不 Root、不改源码、不改安装包、不改现有 VPN 配置”，解密上述原版应用的全部 HTTPS。计划以寻找并验证合法可用入口为先，不承诺通过更换代理工具就能解决证书信任。

本计划交付不等于功能实现；技术门槛未通过前，不进入原版应用解密产品化和发包。

## 二、约束

- 不 Root、不解锁启动引导程序、不利用系统漏洞、不降低系统安全设置。
- 不修改、重签、替换原 APK；不读取或复制登录凭据，不卸载、不清数据。
- 不改原 VPN 的节点、订阅、规则、DNS 或默认路由；VPN 保持开启。
- 不启动会替换原 VPN 的第二个 VpnService。
- 诊断默认只读，不自动安装 CA、辅助应用、设备管理配置或 Frida Gadget。
- 若后续确需临时转发、测试证书或私有诊断出口，其具体操作必须另有对应授权；之前其他试验的临时授权不能自动复用。
- 不把 ADB 在线、代理连通、CONNECT、TLS 握手、浏览器对照、应用日志或密文 PCAP 标为目标应用解密成功。

## 三、现状与技术路线

已具备：设备发现、真机日志、Android AP-0 只读能力核查、mitmproxy/exporter、接口展示与断点引擎。优先复用 capture_console/android_physical_capabilities.py，不另起重复诊断命令体系。

当前四个原版包均不可调试；PokeHub 既有代理试验显示用户 CA 不被接受，不能由此直接断言存在证书锁定。MelodyCraft/Wishly 尚缺新的原版业务解密实测。

| 路线 | 采用条件 | 本期定位 |
| --- | --- | --- |
| 原版现有诊断入口 | 原版已具备可授权启用的正文或 TLS 会话密钥导出能力 | 优先寻找；必须证明确实覆盖业务请求 |
| 受信任代理 | 目标网络栈实际信任测试 CA，且有不破坏原 VPN 的已授权接入路径 | 条件支持，不能依据 CA 已安装就准入 |
| PCAP + 目标 TLS 密钥 | 目标端已合法导出本次会话密钥，且能取得对应内层 TLS 报文 | 条件试验；VPN 外层密钥不能替代应用 TLS 密钥 |
| 服务端采集 | 获得业务方 TLS 终止点或网关采集权限，记录足够完整且可关联 | 备选；明确标为服务端视角，不能冒充手机原始报文 |
| Frida / Gadget / 改包 | 需要 Root、可调试构建或修改运行包 | 不纳入当前边界 |
| Reqable / PCAPdroid / WireGuard / Shizuku | 各工具自己的接入与权限前提 | 不作为自动解密捷径；不为重复失败安装工具 |

测试源码不是线上构建证明；引擎字符串、manifest 和安装来源只作线索。来源与已知证据见 android-nonroot-feasibility-20261110.md。

## 四、阶段安排

### NR-0：能力检查及证据基线

目标：明确“设备已连接、流量可接入、HTTPS 可解密、业务正文已捕获”四个不同层级。

范围：复用 capture_console/android_physical_capabilities.py、device_discovery.py、foreground.py；新增诊断模型放在独立小模块，不继续堆积 runner.py/app.py。

实施顺序：
1. 为设备断开、未授权、多个设备、应用未安装、不可调试、命令超时编写失败测试。
2. 明确目标 serial 与 package，不默认选择第一台设备；核对版本、用户空间及 APK 身份。
3. 只读收集调试属性、现有代理/VPN 可见状态；不可读取项返回未知，不猜测为正常。
4. 返回原因、可行路线和缺失条件，不自动修复需要改手机配置的项目。

验收：每条探测命令有时限和输出上限；未知不准入；切换设备或应用不复用旧结论；诊断不执行 settings put、证书安装、root、VPN 切换或应用重装。Play 安装来源不单独证明包未修改。

### NR-1：确认真正的正文出口

前提：NR-0 基线完成。以 PokeHub 为第一目标，再分别检查其余三个应用。

步骤：
1. 核查原版公开诊断设置、厂商说明及已授权可读信息，不扫描手机私有账号数据。
2. 查明现有诊断出口是否支持完整业务头、正文和响应关联，还是仅支持日志/性能信息。
3. 如存在 TLS 密钥出口，验证其由原版实际 TLS 会话生成，不将环境变量或普通日志当作密钥能力。
4. 如考虑服务端采集，先核实访问权限与字段完整度；当前已知没有管理权限，不能直接进入该路线。
5. 每个候选记录：假设、所需权限、最小试验、预期证据、失败原因、下一步。相同条件下不重复已有失败试验。

验收：至少一个候选具备可执行的接入方法、明确授权及目标原版证据后，才进入 NR-2。没有候选则记录 BLOCKED，不以完成调研标记完整抓包已实现。

### NR-2：隔离最小原型验证

前提：NR-1 已找到实际可用入口。当前未满足，本阶段不预先假定代理、密钥导出或服务端路线已经可用。

步骤：
1. 在独立本机测试目录验证解析、请求响应配对和资源限制，不修改正在使用的桌面服务。
2. 先用自有 HTTPS 夹具验证请求头/JSON/表单、响应头/JSON/压缩内容、无正文响应和异常结束。夹具通过仅证明原型机制。
3. 在保持原包身份、VPN 和配置边界的情况下，启动原版并触发只读业务操作。
4. 对请求/响应记录唯一关联标识、采集位置和完整性；脱敏保存证据，不保存生产登录凭据到仓库。
5. 停止原型，回收本项目资源，检查应用和网络正常。不掌握 VPN 私有状态时，明确要求用户确认，不宣称全部配置已自动恢复。

硬性验收：原版至少三个不同业务接口、一次重复请求、一次页面切换，请求和响应均可关联；有正文时展示真实完整内容，无正文时明确说明。域名、TLS 记录和第三方 SDK 流量不能代替业务接口。

停止条件：再次出现不受信任 CA 且没有新信任机制、需要改包或提权、需要覆盖原 VPN、无合法密钥来源。停止后保留失败结论，不叠加改动。

### NR-3：接入桌面端

前提：NR-2 已对指定原版应用通过。仅将已验证路线产品化，其他应用仍分别显示未验证或不支持。

建议模块边界：
- 后端：复用 android_physical_capabilities.py；新增 android_capture_capabilities_api.py、android_capture_admission.py，分别负责只读接口和启动准入。
- 接入：根据 NR-2 的实测路线增加一个独立采集适配器；传输控制、正文归档、展示复用既有功能，不同时实现多种猜测路线。
- 桌面：新增 AndroidCaptureCapabilityModels.swift、AndroidCaptureCapabilityView.swift；在 APIClient.swift、抓包页接入，文案纳入既有 AppCopy。
- 测试：新增 test_android_capture_capabilities.py、test_android_capture_admission.py，以及 AndroidCaptureCapabilityTests.swift。

建议只读接口：GET /api/devices/{device_id}/capture-capabilities?package={package}。包名/设备需严格校验，调用不改变手机；返回检查时间、身份、证据与判定，不返回 CA 私钥、VPN 密码或原始敏感日志。

判定字段分开：transport、tls、business_http 各为 unknown/passed/failed；overall 为 checking/needs_action/unsupported/ready。只有 NR-2 证据对应当前设备、原包身份和当前接入条件时才能为 ready；版本或连接条件改变后失效。不能仅凭 debuggable=false 判断所有路径都不可用。

桌面交互：连接手机 → 打开应用 → 检查抓包条件 → 条件满足时开始抓包。失败显示具体原因，例如“应用未信任抓包证书，当前无法解密 HTTPS”，不反复提示“准备环境”。未解密时禁用正文编辑与断点，而不是伪造空响应。

验收：未知/失败不可开始；设备切换和重连不会沿用旧准入；已授权临时资源按所有权清理；现有模拟器/iPhone 抓包不回归。所有代码按失败测试、最小实现、通过测试、单阶段提交的顺序推进。

### NR-4：多应用与分发验收

前提：桌面端具备至少一条实测通过的免 Root 真机路线。不把四个应用必须全部通过写成无依据的承诺。

| 对象 | 必测内容 | 结果口径 |
| --- | --- | --- |
| PokeHub | 登录态保留、只读页面、三个业务接口和 Request/Response | 通过或明确具体阻塞 |
| StickerHub | 正式包身份、业务请求响应、媒体流量区分 | 独立验收，不复用 PokeHub 结论 |
| MelodyCraft | 业务与音频/下载区分、正文大小和超时 | 未读取媒体不等于请求失败 |
| Wishly | 业务 JSON、空响应、页面切换 | 不以域名可见判定解密通过 |
| 第二台 Android | 新设备授权、版本差异、证据失效 | 没有设备则记未覆盖 |
| 既有能力 | Android 模拟器、iPhone、日志、停止、归档、断点 | 不改变原协议和用户配置 |

正文资源基线：沿用现有有界预览及文件归档机制，测试 256 KiB、2 MiB、20 MiB 响应及慢正文取消；大文件不整体载入 SwiftUI，不复制无限日志。无法完整保存时必须标记截断或失败，不能展示为完整正文。采集协议不承诺覆盖所有长连接、QUIC、应用层二次加密和无限流。

仅在用户另行要求发布且验收通过后，构建桌面端、验证签名、安装说明和下载产物；本计划不授权推送、合并或发布。

## 五、验收命令与证据要求

实施时按变更范围运行，计划阶段不执行构建或手机实验。

```bash
python -m unittest -v tests.test_android_capture_capabilities tests.test_android_capture_admission
python -m unittest discover -s tests
swift test --package-path macos-native
git diff --check
```

新增测试文件由 NR-3 建立；此前 NR-0/NR-1 使用现有探测测试和对应阶段新增用例，不提前执行不存在的测试。集成测试使用模拟 ADB 与隔离服务，不自动触碰真实手机或生产业务。

每项实机证据包含时间、设备/原包身份、接入方式、前后可读状态、触发动作、Request/Response 关联及停止清理结果。设备标识对外脱敏；原始正文仅保留在本机受控目录，设置大小/期限并提供删除入口。鉴权头、Cookie、Token、CA 私钥和 VPN 配置不进入提交或公开截图。

## 六、排期与决策

按工程工作日估算，不计外部权限、手机必要确认与新的安全限制：

| 阶段 | 工作量 | 进入下一阶段的门槛 |
| --- | --- | --- |
| NR-0 | 0.5–1 天 | 只读证据与状态分类可靠 |
| NR-1 | 1 天时间盒 | 有满足约束的可用候选；否则停止并记录阻塞 |
| NR-2 | 1–2 天 | 原版真实业务 Request/Response 通过 |
| NR-3 | 2–3 天 | 桌面启动、展示、停止及兼容回归通过 |
| NR-4 | 1–2 天 | 指定设备/应用矩阵及分发边界有证据 |

全部技术门槛通过时，预估 5.5–9 个工程工作日；不是突破保证。NR-1 无候选或 NR-2 触发停止条件时，不继续消耗完整产品化排期。

关键决策：保持当前全部限制时，优先完成可行性门槛，而不是先开发新的手机抓包应用。若门槛仍未满足，只能等待原版已有诊断能力或服务端授权等新前提；诊断构建、Root 和改包均不是默认降级方案。能力检查完成也不能替代原版完整抓包目标完成。
