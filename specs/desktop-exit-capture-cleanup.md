# 桌面端退出抓包清理规格

## 问题

抓包脚本通过 `screen` 启动 mitmproxy、导出器和 Frida hook。这些进程会脱离桌面后端的父进程，因此仅终止 FastAPI 后端不能结束抓包。数据库仍保留 `running` 任务，桌面端重开后会按真实存活链路恢复旧任务，并阻止安装应用。

## 行为

1. 桌面端完全退出时，仅当本次桌面端拥有或已安全接管本机后端，才调用 `POST /api/desktop/stop-captures`。
2. 后端遍历所有活动任务，按设备停止本项目抓包进程、清除 Android 全局抓包代理，并把任务更新为 `stopped`。
3. 同一设备只清理一次；单个设备失败不能阻止其他设备继续清理。
4. 清理不调用设备释放或模拟器关闭，不删除抓包输出、应用、账号或登录态。
5. 桌面端等待清理请求的时间必须有上限；成功、失败或超时后都继续结束本机后端。
6. 普通关闭窗口但应用未退出时不触发该流程；仅 `applicationWillTerminate` 触发。

## 接口

`POST /api/desktop/stop-captures`

- 返回 `ok`、`stopped_count` 和逐设备 `results`。
- `results` 只包含清理结果摘要；现有单任务停止接口保持兼容。
- 即使底层停止命令失败，已确认的活动任务也要结束数据库活动状态，避免重开后永久误锁；失败详情留在结果中供诊断。

## 验收

- Python 回归验证多设备清理、代理清理、状态落库、结果保留和不关闭模拟器。
- Swift 回归验证桌面端在终止自有后端前发送清理请求，外部后端不受影响，接口超时不阻塞退出。
- 真实抓包状态下退出 `.app`：本项目抓包端口和 Frida/exporter 进程消失，模拟器仍在线，原输出目录仍存在。
- 重开 `.app`：`active_session` 为空，安装页不再显示“当前模拟器正在抓包”。
