# BP-0 隔离传输能力与准入记录

日期：2026-11-04。基线：`c4a7d6c`，工作树 `codex/ios-device-trial`。

## 范围与结论

只修订计划与新增测试夹具，没有修改 `capture_console/`、`scripts/`、Swift、依赖、发布文件或正在运行的应用。所有实验仅使用 `127.0.0.1` 随机端口、临时目录、自签测试 CA，客户端与代理显式验证本次测试 CA；不安装系统证书、不读取手机凭据、不连接手机、不更改 VPN、节点或系统代理。

**传输实验可复现，不等于产品安全准入通过。当前结论 NO-GO：不能把此原型接入桌面端，也不进入 BP-1。** 小包暂停、编辑、放行成立，但收集期间取消及头暂停的资源约束未成立。原型无生产入口，关闭/跳过不安全能力不冒充完整断点已经完成。

四项评审已写入计划：

1. 心跳/控制通道暂时失联和所属进程真正退出分开处理；后者有限排空后回收，不遗留无人管理的代理。现有 iOS `maintain` 的关闭顺序在 BP-2 修改，本轮没有改变它。
2. 正文收集有独立总期限和空闲期限；20 个名额覆盖收集与暂停；无法按时收敛的模式不得启用。
3. Query/Header/方法/状态码等任何有效修改都保存原始元数据；未改正文共享引用。归档实现与双版本验证属于 BP-2，未在本轮声称实现。
4. 默认匹配 scheme、host、有效 port，不跨 origin；从接口自动带入，不增加手机域名配置。

## 可重复执行

从功能工作树根目录、已安装 `requirements-console.txt` 的 Python 环境执行：

```bash
CAPTURE_TEST_BREAKPOINT_TRANSPORT=1 python -m unittest tests.test_breakpoint_transport -v
```

默认未设置该环境变量时，压力实验跳过，避免日常测试意外创建代理。完整套件是能力实验，包含明确断言限制仍存在的负对照，以及输出 `memory_gate_pass` 的内存观测；绿色实验结果不能解释为所有能力通过。启用严格安全门槛可重现拒绝准入：

```bash
CAPTURE_TEST_BREAKPOINT_TRANSPORT=1 CAPTURE_REQUIRE_BP0_SAFE=1 python -m unittest \
  tests.test_breakpoint_transport.BreakpointTransportTests.test_slow_collection_kill_does_not_close_transport_negative_control \
  tests.test_breakpoint_transport.BreakpointTransportTests.test_h1_request_header_memory \
  tests.test_breakpoint_transport.BreakpointTransportTests.test_h2_stream_memory_candidate -v
```

此严格命令预期非零，原因分别是收集取消未生效、头暂停内存超限、H2 压力基线/候选内存超限。不得删除这些检查或提高门槛以宣布上线。

## 方法与证据约束

- 依赖：mitmproxy 12.2.3、h2 4.3.0、h11 0.16.0、Brotli 1.2.0；使用现有包，不安装 pytest/httpx。
- 真正的 TLS client -> 独立 DumpMaster 子进程 -> TLS origin；每个测试新 worker/CA/端口；控制走继承的 stdin/stdout 管道，不开放控制 HTTP 端口。
- TLS ALPN 与源站协议均核对 HTTP/1.1 或 h2，不能只凭请求头声称 H2 成功。
- 源站收到请求头时即计数，客户端收到最终响应头时即标记；断点期间检查两侧，不只检查响应正文。
- 100 MiB 使用 16 KiB 分块和增量 SHA-256，两端只保留 256 KiB 预览；夹具事件队列有界。RSS 采样来自独立 worker 的 `getrusage().ru_maxrss`，macOS 单位 bytes；各协议/暂停阶段单独进程，避免高水位串扰。
- 压力结果是本机快源站/消费者速差条件下的峰值增量，不推断所有正常手机流量都会出现同样内存。H2 另跑关闭断点的相同基线，区分底层缓冲与本功能新增开销。
- 每个用例清理自身客户连接、源站、worker 和临时目录；正常回收失败才终止持有的具体测试子进程，不按进程名杀进程，不操作已有端口。

## 初轮发现与处置

首次 10 项运行有 2 项失败，保持 BP-0 未通过状态继续排查：

- 头暂停第二轮断言把第一轮已经发送的源站记录也算入，修正为每个协议独立进程和独立记录；这是夹具错误，不是产品修复。
- H2 的 100 MiB 流式测试超出 64 MiB 额外 RSS 门槛。补关闭断点基线后同样复现；未调整生产依赖或流式阈值，保留 NO-GO，并将观测与严格准入两种命令分开。
- 本机 Flow.kill 源码也明确记录了在途取消限制；实验在已调用 kill 后继续观察连接及名额，直到客户端主动断开才回收。不将 `flow.live=false` 当作传输已关闭。
- Brotli 1.2.0 的 `output_buffer_limit` 是缓冲阈值，不是严格的返回字节上限；4 MiB 重复数据实测单次可返回 491456 bytes。原型拒绝超过 256 KiB 的结果，不把该参数声称为精确分配上限；生产解码器仍需独立预算验证。

## 最终实测记录

以下为独立复核补强后的完整运行：18 项实验，35.475 秒，实验断言全部通过（包含负对照，不代表准入通过）。HTTP/1.1 和 h2 均完成实际 TLS 往返。

| 实验 | 结果 |
| --- | --- |

| 原样放行与压缩编辑 | gzip/deflate/br 两协议原始压缩字节不变；修改后可解压且长度一致；重复请求头保留 |
| 压缩膨胀/坏编码 | 4 MiB 解码源被拒绝进入编辑，明确收到请求/响应两阶段 body_not_editable 事件，active/pending 均归零，无 addon ERROR；原始压缩字节仍正常转发，worker 额外峰值 9469952 bytes |
| 未知长度 | 小包可暂停，2 MiB chunked/H2 越界流式转发，大小与 SHA-256 一致，无重复丢失 |

## 尚未交付的能力

本轮没有 UI、认证控制 API、生产规则引擎、100 条规则性能、单次规则回收实现、原始/有效版本持久化、桌面所有权/租约清理适配或真机验收。所有这些仍属于后续阶段，不能用本原型替代。暂停中的有限恢复可用，不代表收集中能够恢复。

下一步保留在 BP-0：先解决有公开、可维护边界的收集取消和背压方案，再重新运行严格门槛。不能通过关闭整个共享 H2 连接影响其他流、修改 site-packages、取消既有大包保护或更改用户 VPN 来绕过。若只能缩小首版支持范围，应在能力矩阵明确限制后重新验证，而非默认放开此原型。
