## 范围与结论

只修订计划与新增测试夹具，没有修改 `capture_console/`、`scripts/`、Swift、依赖、发布文件或正在运行的应用。所有实验仅使用 `127.0.0.1` 随机端口、临时目录、自签测试 CA，客户端与代理显式验证本次测试 CA；不安装系统证书、不读取手机凭据、不连接手机、不更改 VPN、节点或系统代理。

**当前结论：BP-0隔离原型DONE，允许进入BP-1引擎/控制开发，不允许直接接入产品。** 续修最终36项严格测试通过，原始18项能力/负对照及37项既有回归通过；具体支持范围和结果见末节。仅mitmproxy 12.2.3适配的H1->H1/H2->H2通过；大包/未知长度跳过头编辑，不承诺无限暂停或所有协议。

**首轮历史结论NO-GO保留：原addon-only候选仍不可用。** 小包暂停、编辑、放行成立，但收集期间取消及头暂停的资源约束未成立。以下首轮记录及预期失败命令不删除；原型无生产入口，不冒充桌面断点已经完成。

四项评审已写入计划：

1. 心跳/控制通道暂时失联和所属进程真正退出分开处理；后者有限排空后回收，不遗留无人管理的代理。现有 iOS `maintain` 的关闭顺序在 BP-2 修改，本轮没有改变它。
2. 正文收集有独立总期限和空闲期限；20 个名额覆盖收集与暂停；无法按时收敛的模式不得启用。
3. Query/Header/方法/状态码等任何有效修改都保存原始元数据；未改正文共享引用。归档实现与双版本验证属于 BP-2，未在本轮声称实现。
4. 默认匹配 scheme、host、有效 port，不跨 origin；从接口自动带入，不增加手机域名配置。


## 方法与证据约束

- 依赖：mitmproxy 12.2.3、h2 4.3.0、h11 0.16.0、Brotli 1.2.0；使用现有包，不安装 pytest/httpx。
- 真正的 TLS client -> 独立 DumpMaster 子进程 -> TLS origin；每个测试新 worker/CA/端口；控制走继承的 stdin/stdout 管道，不开放控制 HTTP 端口。
- TLS ALPN 与源站协议均核对 HTTP/1.1 或 h2，不能只凭请求头声称 H2 成功。
- 源站收到请求头时即计数，客户端收到最终响应头时即标记；断点期间检查两侧，不只检查响应正文。
- 100 MiB 使用 16 KiB 分块和增量 SHA-256，两端只保留 256 KiB 预览；夹具事件队列有界。RSS 采样来自独立 worker 的 `getrusage().ru_maxrss`，macOS 单位 bytes；各协议/暂停阶段单独进程，避免高水位串扰。
- 压力结果是本机快源站/消费者速差条件下的峰值增量，不推断所有正常手机流量都会出现同样内存。H2 另跑关闭断点的相同基线，区分底层缓冲与本功能新增开销。
- 每个用例清理自身客户连接、源站、worker 和临时目录；正常回收失败才终止持有的具体测试子进程，不按进程名杀进程，不操作已有端口。

## 初轮发现与处置

首次 10 项运行有 2 项失败，保持 BP-0 未通过状态继续排查：

- 头暂停第二轮断言把第一轮已经发送的源站记录也算入，修正为每个协议独立进程和独立记录；这是夹具错误，不是产品修复。
- H2 的 100 MiB 流式测试超出 64 MiB 额外 RSS 门槛。补关闭断点基线后同样复现；未调整生产依赖或流式阈值，保留 NO-GO，并将观测与严格准入两种命令分开。
- 本机 Flow.kill 源码也明确记录了在途取消限制；实验在已调用 kill 后继续观察连接及名额，直到客户端主动断开才回收。不将 `flow.live=false` 当作传输已关闭。
- Brotli 1.2.0 的 `output_buffer_limit` 是缓冲阈值，不是严格的返回字节上限；4 MiB 重复数据实测单次可返回 491456 bytes。原型拒绝超过 256 KiB 的结果，不把该参数声称为精确分配上限；生产解码器仍需独立预算验证。

### 修复及限制

- 慢正文：绝对10秒/空闲3秒分别计时，空DATA不刷新；测试缩短到0.4/0.2秒。真正向目标传输状态机发送取消事件，H1结束目标连接、H2取消目标流，不再只调用flow.kill。名额释放、同一H2连接健康流仍能完成均有断言。
- 大包：正文编辑仍限制256KiB；头编辑只允许已知且小于128KiB。大包/未知长度在暂停前标记跳过并原样流式传输。并非“暂停100MiB还能无限编辑”。H2没有长度时按END_STREAM判定空正文。
- H2：65535逐流接收窗口、最多32并发流；逐流256KiB水位包含暂停队列、上游并发等候队列和发送缓存。连接级窗口继续返还，使健康流不被慢流拖住；这些是水位而非进程精确分配上限，额外在途帧/协议/解码内存用RSS验收。
- 空/细碎帧：无内容DATA不入队，不续计时；队尾按16KiB合并，保留字节和END_STREAM。RST/GOAWAY清理延迟信用和trailer；同批DATA+GOAWAY不再给已关闭连接返还窗口。
- 上游并发：没有获准发送的请求取消后从排队移除，不再被晚些时候发往源站。GOAWAY/EOF将已发送和未发送请求分别正确结束，不混淆上下游流ID。
- H1：等待源站TLS时，只阻塞对应来源读任务、不阻塞事件派发；持续积压的读取等待最多10秒，事件唤醒不续期。客户端断开无法即时读到EOF时，期限回收目标客户端及其自有上游握手；等待期间主动退出也正常回收。超过期限明确终止，不宣称无限慢源站无损恢复。
- 响应头可能排在仍执行的request hook之后；在response对象创建前保留计时状态、不解引用None。两条分支以真实HTTPFlow/HttpStream状态契约RED/GREEN覆盖，不把该契约测试描述为真实网络竞态复现。

### 最终压力证据

每项独立worker；以下为**额外峰值RSS bytes**，门槛统一为67,108,864 bytes（64MiB），没有提高门槛：

| 场景 | H1 | H2 |
| --- | --- | --- |
| 100MiB请求，头编辑自动跳过 | 4,587,520 | 3,801,088 |
| 100MiB响应，头编辑自动跳过 | 4,308,992 | 3,325,952 |
| 100MiB流式，断点候选开启 | 4,112,384 | 3,588,096 |
| 100MiB流式，断点关闭但安全传输适配保留 | 未单设此组 | 3,309,568 |

上述转发大小及增量SHA-256全部一致。原始无适配H2基线在本轮重跑仍约128MiB额外峰值，风险未被夹具掩盖。

- 延迟上游TLS的100MiB H1上传：额外4,177,920 bytes，队列不到128项，生产者确实等待；恢复后100MiB哈希一致。永不恢复并断开客户端的独立测试中，1秒测试等待期限后活跃连接归零，worker存活；另测等待时shutdown在3秒内退出0。
- H2慢消费者：额外3,620,864 bytes，恢复前源站只发送393,210 bytes，恢复后完整哈希；同连接的健康大请求不被阻塞。
- 20路H2慢消费者：总量167,772,160 bytes（160MiB），额外22,183,936 bytes（约21.2MiB），均完整结束。
- 上游MAX_CONCURRENT_STREAMS=1：排队上传被限制在311,296 bytes，额外819,200 bytes；取消后源站没有收到这个请求。
- 压缩膨胀/坏编码：4MiB解码源拒绝编辑，原样透传，额外9,191,424 bytes；不是取消原有压缩保护。
- 未命中延迟：关闭p95=23.36ms、开启16.42ms，差-6.94ms；每组20次，仅粗粒度抽样，负差不作加速结论。上一完整35项矩阵差-0.15ms，均未见超过5ms新增延迟。
